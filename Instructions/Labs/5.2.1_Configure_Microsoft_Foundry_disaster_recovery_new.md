# AI Ready Manage hands-on exercise: Configure Microsoft Foundry hub disaster recovery

## Background information
Microsoft strives to ensure that Azure services are resilient, but unplanned service outages might occur. Foundry does not provide automatic failover or disaster recovery, so creating a disaster recovery plan is essential. Such a plan should incorporate multi-region deployment of Foundry and associated resources, maximize recovery capabilities, include high availability provisions, and support failover to another Azure region.

Resiliency of Foundry Agent Service relies on the shared responsibility model. The specifics depend on the environment configuration mode. In Standard mode, Microsoft operates the control plane and capability host platform components, while you as a customer handle the durability of any stateful dependencies within your management scope. In Basic mode, these data components are Microsoft-managed, limiting your ability to customize recovery options. 

When operating in Standard mode, Microsoft Foundry projects can attach optional resources based on workload patterns, such as retrieval, orchestration, monitoring, and integration. The corresponding service categories include Azure Storage, Cosmos DB, AI Search, Key Vault, ACR, Logic Apps, Functions, Event Grid, Application Insights, SharePoint, and Microsoft Purview. You have the flexibility to configure redundancy, backup, and replication settings of these services in accordance with your resiliency requirements. 

In addition, to prevent accidental deletions, you should consider applying delete resource locks to critical resources such as Foundry accounts, Azure Cosmos DB accounts, AI Search services, and Storage accounts. However, you should keep in mind that these locks prevent deletion of the resource itself, but they do not protect the data within containers, indexes, or blobs. For additional protection, you can combine locks with Azure Policy denyAction effects to block resource provider delete requests. You might want to also leverage features such as soft delete for Azure Blob Storage and continuous backups for Cosmos DB. 

In general, your resources should be configured to support recovery before incidents occur. Recommended practices include using user-assigned managed identities (instead of system assigned, which lifecycle is inherently tied to their respective resources), enabling multi-region replication and system-managed failover for Cosmos DB, and geo-zone-redundant storage (GZRS) for Storage accounts.

Provisioning standard environments is not available directly from the Azure portal, but you can implement them either programmatically or via deployment templates. Sample Azure Resource Manager and Bicep templates are available from the [foundry-samples GitHub repository](https://github.com/azure-ai-foundry/foundry-samples/tree/main/infrastructure/infrastructure-setup-bicep/17-private-network-standard-user-assigned-identity-agent-setup). These templates support provisioning a Foundry account and project, deploying a model, and configuring authentication using user-assigned managed identity. With the Standard configuration option, you can choose between automatic provisioning of the required Azure resources or referencing pre-provisioned resources via template parameters, giving you full control over how Azure Storage, Azure Cosmos DB, and Azure AI Search are connected to your project.

## Scenario
Your company is building a centralized AI platform on Microsoft Foundry to support enterprise knowledge management and decision support across multiple business units, with a focus on enabling intelligent document retrieval, automated analysis of internal reports, and conversational insights while ensuring strict compliance and data ownership controls. To achieve operational resilience, the team will deploy a Standard agent environment using pre-provisioned, customer-owned Azure resources, including geo-redundant Azure Storage accounts and Azure Cosmos DB with continuous backup and failover configured, integrated via a user-assigned managed identity. The deployment will be automated using template-based methods that reference these resources, creating a Foundry account and project, binding the resources to the project, and configuring an agent model to leverage them, establishing a secure, highly available, and centrally managed foundation for scalable AI-driven services across the organization.

## Prerequisites
- **Azure subscription**: If you don't have an Azure subscription, [create a free account](https://azure.microsoft.com/free/) before you begin.
- **Permissions**: To create Azure AI Services resources, you should have the Owner role assigned at the Azure subscription.
- **Familiarity with Microsoft Foundry resource types**: To learn more, refer to [Choose an Azure resource type for AI foundry](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/resource-types).

### Task 1: Implement a resilient Azure Storage account for BYO file storage

1. Start a web browser, navigate to the Azure portal at [https://portal.azure.com](https://portal.azure.com) and sign in by providing the credentials of a user account which has the Owner role assigned at the Azure subscription level.
1. In the web browser displaying the Azure portal, use the **Search** text box at the top of the page to search for **Storage accounts** and, in the list of results, select **Storage accounts**.
1. On the **Storage accounts \| Storage accounts (Blobs)** page, select **+ Create**.
1. On the **Basics** tab of the **Create storage account** page, specify the following settings (leave others with their default values) and select **Next**:

   |Setting|Value|
   |---|---|
   |Subscription|The name of the Azure subscription you are using in this exercise|
   |Resource group|The name of a new resource group **foundry-bcdr-RG**|
   |Storage account name|Any globally unique name between 3 and 24 in length consisting of lowercase letters and digits, starting with a letter|
   |Region|The name of the Azure region which supports Microsoft Foundry standard agent setup|

   >**Note**: For the list of Azure regions to choose from, refer to the values of the **location** parameter in the [**azuredeploy.json**](https://github.com/azure-ai-foundry/foundry-samples/blob/main/infrastructure/infrastructure-setup-bicep/41-standard-agent-setup/azuredeploy.json) Azure Resource Manager template. Verify that you can provision an Azure AI Search instance and Azure Cosmos DB account in the same region and in the paired up region.

   >**Note**: Use the information provided in the [Azure regions list](https://learn.microsoft.com/en-us/azure/reliability/regions-list) to identify the region which is paired up with the one you selected for the deployment. 

   |Preferred storage type|**Azure Blob Storage or Azure Data Lake Storage Gen 2**|
   |Performance|**Standard**|
   |Redundancy|**Geo-redundant storage (GRS)**|
   |Make read access to data available in the event of regional availability|Enabled|

   >**Note**: You also have the option to enable geo priority replication, which guarantees that Blob Storage data is geo-replicated within 15 minutes.

1. On the **Advanced** tab, specify the following settings (leave others with their default values) and select **Next**:

   |Setting|Value|
   |---|---|
   |Enable storage account key access|**Disabled**|

1. On the **Networking** tab, ensure that the **Public network access** option is set to **Enable**, the **Public network access type** is set to **Enable from all networks**, and then select **Next**.
1. On the **Data protection** tab, ensure that the settings **Enable soft delete for blobs** and **Enable soft delete for containers** are enabled, and then select **Review + create**.
1. On the **Review + create** tab, wait for the validation process to complete, and then select **Create**.

   >**Note**: Wait for the resource provisioning to complete. This should take less than one minute. 

1. On the **Deployment** page, select **Go to resource**.
1. On the **Overview** page of the newly provisioned storage account, in the vertical menu on the left side, expand the **Settings** section and select **Locks**.
1. On the **Locks** page of the storage account, select **+ Add**.
1. In the **Add lock** dialog box, specify the following settings and select **OK**:

   |Setting|Value|
   |---|---|
   |Lock name|**block_delete**|
   |Lock type|**Delete**|

### Task 2: Implement a resilient Azure Cosmos DB account for BYO thread storage

1. In the web browser displaying the Azure portal, use the **Search** text box at the top of the page to search for **Azure Cosmos DB** and, in the list of results, select **Azure Cosmos DB**.
1. On the **Azure Cosmos DB** page, select **+ Create**.
1. On the **Create an Azure Cosmos DB account** page, on the **Recommended APIs** tab, on the **Azure Cosmos DB for NoSQL** tile, select **Create**.
1. On the **Basics** tab of the **Create Azure Cosmos DB Account - Azure Cosmos DB for NoSQL** page, specify the following settings (leave others with their default values) and select **Next: Global distribution**:

   |Setting|Value|
   |---|---|
   |Workload Type|**Development/Testing**|
   |Subscription|The name of the Azure subscription you are using in this exercise|
   |Resource group|**foundry-bcdr-RG**|
   |Account name|**foundrybcdraccount**|
   |Availability Zones|**Enable**|
   |Location|The name of the same Azure region you specified when provisioning the storage account earlier in this exercise|
   |Capacity mode|**Provisioned throughput**|
   |Apply Free Tier Discount|**Apply**|
   |Limit the total amount of throughput that can be provisioned on this account|Enabled|

   >**Note**: You might need to disable support for availability zones if the Azure regions you target for deployment are not available.

   >**Note**: The provisioned throughput capacity mode is required to enable multi-region replication.

   >**Note**: You might not be able to apply free tier discount if you already have an Azure Cosmos DB account using this feature.

1. On the **Global distribution** tab, specify the following settings (leave others with their default values) and select **Next: Networking**:

   |Setting|Value|
   |---|---|
   |Geo-Redundancy|**Enable**|
   |Multi-region Writes|**Disable**|

   >**Note**: The geo-redundancy might be automatically disabled if you do not have the option to provision a Cosmos DB account replica in the paired region.

1. On the **Networking** tab, ensure that **Connectivity method** is set to **All networks** and then select **Next: Backup policy**.
1. On the **Backup policy** tab, specify the following settings (leave others with their default values) and select **Next: Security**:

   |Setting|Value|
   |---|---|
   |Backup policy|**Continuous (30 days)**|

   >**Note**: Continuous backup policy provides backup window of 30 days and you can restore to any point in time within this window.

1. On the **Security** tab, set **Key-based Authentication** to **Disabled** and then select **Review + create**.
1. On the **Review + create** tab of the **Create Azure Cosmos DB Account - Azure Cosmos DB for NoSQL** page, wait for the validation process to complete, and then select **Create**.

   >**Note**: Wait for the resource provisioning to complete. This might take about 3 minutes.

1. On the **Deployment** page, select **Go to resource**.
1. On the **Overview** page of the newly provisioned storage account, in the vertical menu on the left side, expand the **Settings** section and select **Locks**.
1. On the **Locks** page of the storage account, select **+ Add**.
1. In the **Add lock** dialog box, specify the following settings and select **OK**:

   |Setting|Value|
   |---|---|
   |Lock name|**block_delete**|
   |Lock type|**Delete**|

1. In the vertical menu on the left side, in the **Settings** section, select **Replicate data globally**.
1. On the **Replicate data globally** page of the Cosmos DB account, select **Failover policy configuration**.
1. In the failover policy configuration, verify that the read region matches the paired Azure region you identified earlier in this exercise, select the checkbox **I understand and agree to proceed with enabling** and then select **OK**.

   >**Note**: This configuration defines the behavior of service managed failover. 

### Task 3: Create a user-assigned managed identity

1. In the web browser displaying the Azure portal, use the **Search** text box at the top of the page to search for **Managed identities** and, in the list of results, select **Managed identities**.
1. On the **Managed identities** page, select **+ Create**.
1. On the **Basics** tab of the **Create User Assigned Managed Identity** page, specify the following settings (leave others with their default values) and select **Review + create**:

   |Setting|Value|
   |---|---|
   |Subscription|The name of the Azure subscription you are using in this exercise|
   |Resource group|**foundry-bcdr-RG**|
   |Name|**foundrybcdruami**|
   |Region|The name of the same Azure region you specified when provisioning the storage account earlier in this exercise|
   |Isolation Scope|**None**|

   >**Note**: You can set your managed identity's isolation scope value to either None or Regional. None (default) designates that the identity can be used across all regions. Regional restricts the location of resources associated with the managed identity to the one where managed identity is provisioned. For disaster recovery scenarios, you should set the isolation scope to **None**.

1. On the **Review + create** tab of the **Create User Assigned Managed Identity** page, wait for the validation process to complete, and then select **Create**.

   >**Note**: At this point, you could use the sample template available from the [foundry-samples GitHub repository](https://github.com/azure-ai-foundry/foundry-samples/tree/main/infrastructure/infrastructure-setup-bicep/17-private-network-standard-user-assigned-identity-agent-setup) to deploy a Microsoft Foundry resource and the corresponding project using your pre-provisioned resources. 

### Task 4: Perform cleanup

1. Open another tab in the web browser displaying the Microsoft Foundry portal, navigate to the Azure portal at [https://portal.azure.com](https://portal.azure.com) and, if prompted, sign in by providing the same credentials you have been using throughout this exercise.
1. In the Azure portal, use the **Search** text box at the top of the page to search for **foundry-bcdr-RG** and, in the list of results, select **foundry-bcdr-RG**.
1. On the **foundry-bcdr-RG** page, select **Delete resource group**, on the **Delete a resource group** pane, in the **Enter resource group name to confirm deletion** text box, enter **foundry-bcdr-RG**, select **Delete**, and, when prompted for confirmation, select **Delete** again.
